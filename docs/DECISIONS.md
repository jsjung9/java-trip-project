# 설계 결정 기록

## ADR-001: 기존 비밀번호를 로그인 시점에 점진적으로 전환

**상태:** 적용

기존 DB에는 임의 salt를 붙인 단일 SHA-256 해시가 저장되어 있었습니다. 모든 사용자에게 즉시 초기화를 요구하면 운영 전환이 어렵고, 기존 방식을 계속 쓰면 느린 비밀번호 해시가 제공하는 무차별 대입 방어를 얻지 못합니다.

로그인 시 저장값이 `$2`로 시작하면 BCrypt로 검증합니다. 그렇지 않으면 기존 방식으로 한 번 검증한 뒤 성공한 같은 요청에서 BCrypt 해시로 갱신하고 salt를 `NULL`로 바꿉니다. 원문 비밀번호를 저장하지 않으면서 실제 접속 계정부터 자동 이관합니다.

## ADR-002: access token과 refresh token의 저장 위치 분리

**상태:** 적용

access token은 API 호출에 필요하므로 sessionStorage에 두고 짧은 만료 시간을 사용합니다. 장기 refresh token은 HttpOnly·SameSite 쿠키에 두어 애플리케이션 JavaScript가 읽지 못하게 했습니다. 서버 DB의 현재 값과 일치해야 갱신할 수 있고, 성공할 때마다 새 refresh token으로 교체합니다.

개발 HTTP 환경에서는 `security.cookie.secure=false`가 기본값입니다. HTTPS 운영 환경은 반드시 `SECURITY_COOKIE_SECURE=true`에 대응하는 설정으로 실행해야 합니다.

## ADR-003: MyBatis 유지와 서비스 계층 트랜잭션 강화

**상태:** 적용

짧은 포트폴리오 개선에서 ORM으로 전면 교체하면 핵심 문제였던 소유권과 정합성 개선보다 변환 범위가 커집니다. 명시적인 SQL이라는 기존 특성을 유지하고, 서비스가 트랜잭션 경계와 규칙을 담당하도록 책임을 재배치했습니다. Mapper는 관계 행의 실제 변경 여부를 반환합니다.

## ADR-004: 집계 컬럼을 유지하되 관계 데이터로 보정

**상태:** 적용

인기 테마·장소 조회가 빈번하므로 `like_sum`, `score_sum`, `score_count`를 유지합니다. 좋아요는 관계가 바뀐 경우에만 증감하고, 평점은 사용자별 원본 행을 upsert한 뒤 합계와 건수를 다시 계산합니다. 조회 성능을 유지하면서 재시도와 평가 수정에 안전하게 만들었습니다.
